# 다른 앱에서 레시피 추천 v2 쓰기 — 여기서 시작하세요

이 저장소(`alexisnoh37-cell/ontol_recipe_claude`)의 **현재 기준 추천 로직은 v2**입니다. 이 문서는 다른 앱의 개발자나 AI 코딩 도구가 이 로직을 가져다 쓰려고 할 때 **처음 읽는 안내서**입니다. 이 문서만 읽으면 무엇을, 어떤 순서로, 어디까지 하면 되는지 알 수 있게 썼습니다.

## 1. v2가 하는 일 (한 문단)

사용자 정보 6가지를 받습니다. 못 먹는 것(알레르기·절대 안 먹는 재료), 좋아하는 재료, 싫어하는 재료, 매운맛 정도, 음식 종류 선호, 요리 실력입니다. 이 정보로 레시피 1,522개 중에서 추천합니다.

- **추천 형태**: 랜덤 / 내 재료로(지금 바로 · 조금만 사면) / 요리 찾기(요리 이름이나 "오늘은 얼큰한 국물이 끌려" 같은 느낌)
- **처리 순서**:
  1. 못 먹는 레시피를 **규칙으로 먼저 제외**합니다.
  2. 관련 후보를 고릅니다.
  3. 순위와 추천 이유(항목별 점수)는 **Jev(TypeSafe AI, `jev-1.14.0`)** 가 정합니다.
  4. Jev가 실패하면 규칙 점수로 대체합니다.

> README와 `CLAUDE.md`에 남은 "MVP v1"·"LLM 연동은 Phase 2부터"는 초기 단계 설명입니다. 범위 확대는 `docs/decisions.md` D6~D10으로 결정되었고, v1 엔진(`engine/*.py`)은 비교·대체용으로 남아 있습니다.

## 5. 반드시 지킬 안전 규칙

하나라도 바뀌면 알레르기 사용자에게 위험한 레시피가 나갈 수 있습니다. 공용 시험 세트의 `safety_` 사례와 모든 사례의 `must_exclude`가 이것을 검사합니다.

1. **알레르기 판정에 AI(Jev 포함)를 쓰지 않습니다.** 제외는 규칙으로 먼저 끝내고, Jev는 제외를 통과한 후보의 순서만 정합니다. Jev가 목록 밖 레시피를 답해도 무시합니다.
2. **알레르기는 들어 있을 수도 있는 재료(possible)까지 제외**합니다. 선택 재료·고명·기본 양념 줄도 봅니다. 예: 새우 알레르기면 김치(새우젓 포함 가능)가 든 레시피 제외.
3. **알레르기가 있는 사용자에게는 정체를 모르는 재료(미매칭)가 든 레시피를 보여 주지 않습니다.**
4. **절대 안 먹는 재료는 확실히 든(definite) 레시피만 제외**합니다. 포함 가능은 통과시키고 "성분표 확인" 안내를 붙입니다. 종교 등 엄격한 회피는 알레르기 그룹(예: `pork`)으로 받습니다.
5. **매운맛 정도 0~4**는 그 값을 넘는 레시피를 제외합니다. 맛 정보가 없는 레시피는 매운 재료·미매칭 줄·매운 제목이 모두 없을 때만 "맵지 않음"으로 봅니다. **5는 한도 없음**입니다.
6. **모르는 알레르기 그룹·재료 id는 거부**합니다. 조용히 무시하면 제외가 꺼집니다. 오류가 났을 때 문제 값을 빼고 자동으로 다시 보내지 마세요.
7. **알레르기·절대 안 먹는 재료·사용자 id는 Jev(외부)로 보내지 않습니다.** 보유 재료도 먹을 수 있는 것만 보냅니다.
8. 화면에 **면책 문구**와 **성분표 확인 안내**(알레르기 사용자, 가공품이면서 정보 확신도가 낮은 재료)를 보여 줍니다.

## 6. 옮겨 심는 순서 (완료 기준 포함)

1. **데이터 받기**: 이 저장소를 깨끗한 상태로 받아 데이터 묶음을 만듭니다.
   ```
   uv sync
   uv run python scripts/export_v2_bundle.py --out <그 앱의 데이터 폴더>
   ```
   `manifest.json`의 `commit`(출처 커밋)과 `files`(SHA-256)를 그 앱에 함께 커밋합니다. `dirty: true`면 커밋하지 않은 변경이 섞인 것이니 다시 받으세요.
2. **구현**: [`v2_logic_spec.md`](v2_logic_spec.md)의 2~9장 순서대로 구현합니다. 숫자·목록(가중치, 매운 재료, Jev 질문 문구, 후보 수 등)은 코드에 적지 말고 `config.json`에서 읽습니다.
3. **공용 시험 세트 통과**: `tests/shared/v2_cases.json`의 모든 사례를 명세 10장 규칙으로 비교해 통과시킵니다. 이 세트는 그 앱에 복사해 두고, 출처 커밋을 기록합니다. **통과하기 전에는 옮긴 것으로 보지 않습니다.**
4. **Jev 연결**: 서버에서만 `TYPESAFE_API_KEY`를 읽고, 모델은 `config.v2.rerank.model`을 씁니다. 시간 한도·실패 시 규칙 대체를 지킵니다.
5. **실제 데이터 확인**: 데이터 묶음의 `derived.json`(맛 정보 없는 레시피의 "맵지 않음" 추정 결과)과 옮긴 구현의 계산 결과가 같은지 확인합니다.
6. **평가(선택)**: 이 저장소의 `scripts/eval_v2.py`와 같은 평가 세트로 결과를 비교하면 품질 차이를 숫자로 볼 수 있습니다.

## 7. 갱신(이 저장소가 바뀌었을 때)

- 로직·설정·데이터가 바뀌면 이 저장소에서 공용 시험 세트를 다시 만들고(`scripts/make_shared_cases.py`) 커밋합니다.
- 그 앱은 다음 순서로 따라옵니다.
  1. 새 커밋에서 데이터 묶음을 다시 내보내고 공용 시험 세트를 다시 복사합니다.
  2. 실패하는 사례만큼 구현을 고칩니다.
  3. 출처 커밋을 갱신합니다.
- 기준은 항상 **이 저장소의 코드와 공용 시험 세트**입니다. 그 앱에서 규칙을 바꾸고 싶으면, 먼저 이 저장소에서 바꾸고 시험 세트를 갱신하는 것을 권합니다. 그래야 두 곳이 어긋나지 않습니다.
