## 1. 한 줄 제안

**#181이 제안한 "제한적인 사용자 실험"을, 온톨로지 레시피 1,522개와 Jev 순위 판단을 쓰는 "새 추천(베타)"으로 구체화하자**는 제안입니다.

- 기존 추천은 그대로 두고, 켜고 끌 수 있게 옆에 붙입니다.
- 내 재료 활용·AI 질문·룰렛 세 곳의 추천 엔진을 베타에서 v2로 바꿔 봅니다.
- 결과를 보고 정식 통합·일부 채택·접기를 팀이 정합니다.

## 2. 배경

- 팀 앱의 레시피 기능은 팀이 함께 만든 구조(Node 서버 + Supabase, 방식별 규칙)로 동작합니다. 10월 18일에는 이 저장소의 레시피·재료 지식을 스냅샷(`b423cc4`)으로 가져가 "만들 수 있는 레시피" 판정에 쓰고 있습니다(`docs/ontol-recipe-integration.md`).
- 팀 저장소에 영향을 주지 않으려고, 추천 로직 실험은 별도 저장소에서 진행했습니다. 그 뒤 추천 v2를 완성했습니다(이 저장소 PR #13·#14).
- 팀의 Jev 판단 이력은 다음과 같습니다. 이 제안은 그 흐름을 이어받습니다.

| 시점 | 판단 |
|---|---|
| 10-02 식단 선택 | Jev 제거. 후보가 이미 조건을 통과해 차이가 작고, 잴 기준이 없었음 |
| #116 취향 추천 | 미도입. 가상 취향 5개에서 규칙과 최상위가 같았음 |
| **#181 재평가** | 조리 단계·식감 차이에서 Jev의 추가 가치 확인. **"제한적인 사용자 실험을 다시 추진할 근거가 있다."** 다만 전면 도입이나 "좋아할 확률" 표시는 권하지 않음 |
| #184 조리 방식 개인화 | 합성 데이터 비교만 했고 런타임은 바꾸지 않음 |

## 3. 팀 앱의 추천 방식 8가지와 v2의 관계

v2는 **같은 레시피 목록을 쓰는 방식**에만 해당합니다. 별도 메뉴 120종을 쓰는 식단 도구(⑦⑧)는 대상이 아닙니다.

| 팀 앱 방식 | 베타에서 | 설명 |
|---|---|---|
| ② 내 재료 활용 | **v2 `pantry`로 대체** | 4등급(바로 가능·양념만 확인·1~2개 부족·재료 더 필요) → 2묶음(지금 바로·조금만 사면, 대체재 인정). 구매 예정 재료를 보유로 치지 않는 원칙은 같음 |
| ④ AI 질문 | **v2 `dish`로 대체** | 요리명·느낌 문장으로 찾기. Gemini 설명 문장 대신 Jev 항목별 점수로 추천 이유 표시. 음식과 무관한 질문 거절은 팀 앱 쪽에서 유지 |
| ⑥ 오늘 한 끼 룰렛 | **v2 `random`(아무거나) / `pantry`(내 재료 활용)로 대체** | 먹을 수 있는 것 중 취향 쪽으로. "조리 단계나 영상이 있는 레시피만" 조건은 팀 앱에서 유지 |
| ⑤ 계정 취향 배지 | **v2 순위로 흡수** | 취향이 배지가 아니라 순위에 반영됨. 레시피별 좋아요·싫어요는 v2에 아직 없음 → 결정 필요(9장) |
| ① 메뉴로 찾기(배달 대안) | **베타에서 비교 후 결정** | v2 `dish`에 메뉴명("로제 떡볶이")을 넣으면 대체 가능. 다만 팀 앱은 메뉴 300개마다 주재료·조리법·맛 단서를 정해 두었으므로 결과를 비교해 보고 정함 |
| ③ 건강·신체 특성 정렬 | **기존 유지** | v2에 없음. 건강 옵션을 켠 경우의 처리(기존 경로 사용 등)는 결정 필요(9장) |
| ⑦ 식단·예산, ⑧ 한 끼 교체 | **범위 밖** | 별도 메뉴 120종 사용. 바꾸지 않음 |

## 4. 베타가 끝났을 때 사용자가 겪는 장면

1. 마이페이지에서 알레르기(27그룹 중 선택), 절대 안 먹는 재료, 매운맛 정도, 좋아하는 음식 종류, 요리 실력을 입력합니다. 좋아하는·싫어하는 재료는 지금 저장된 것을 그대로 씁니다.
2. "내 재료 활용"을 누르면 **지금 바로 / 조금만 사면**으로 나뉜 레시피가 내 취향 순서로 나옵니다. "조금만 사면"에는 살 재료가 보입니다.
3. 상단 검색에 "오늘은 얼큰한 국물이 끌려"나 "간단한 아침"을 치면 그에 맞는 레시피가 나옵니다.
4. 룰렛을 돌리면 먹을 수 있는 것 중 내 취향 쪽 레시피가 나옵니다.
5. 카드마다 "왜 추천했나"가 항목별(요청·맛·재료 취향·음식 종류·실력·가진 재료)로 보입니다. 확률이나 퍼센트로는 보여 주지 않습니다(6장).
6. 새우 알레르기면 김치가 든 레시피는 어디에서도 나오지 않습니다.
7. 베타 기간에는 설정에서 "새 추천"을 끄면 예전 방식으로 돌아갑니다.

## 5. 근거: 같은 평가 세트로 잰 결과

평가 세트는 44개 요청입니다(기존 기준 시나리오 14 · 테스트 페르소나 20 · 요리 문장 10). 같은 세트를 규칙 순위와 Jev 순위로 각각 돌렸습니다(2026-10-19, jev-1.14.0, 상세 `docs/review/v2_eval.md`).

| 지표 | 규칙 순위 | Jev 순위 |
|---|---|---|
| 안전 위반(엔진과 별도로 다시 판정, 반드시 0) | 0 | 0 |
| 결과 없음 비율 | 0.07 | 0.00 |
| 좋아하는 재료 적중(상위 5) | 0.44 | 0.59 |
| 좋아하는 음식 종류 비율 | 0.41 | 0.47 |
| 싫어하는 음식 종류 비율(낮을수록 좋음) | 0.08 | 0.04 |
| 서로 다른 주재료 수(상위 10) | 13.5 | 20.8 |
| 평균 응답 시간 | 27ms | 353ms |
| 요청당 Jev 입력 토큰 | 0 | 약 3만 |

#181과 이 평가는 서로 다른 것을 쟀습니다. 둘을 합치면 "실제 사용자로 확인할 가치가 있다"는 근거가 됩니다.

- **#181**: 합성 시나리오에서 조리 단계·식감 차이를 구분하는지
- **이 평가**: 실제 레시피 1,522개에서 취향 적중·결과 없음·다양성

한계도 적습니다.

- 위 수치는 모두 **자동으로 잰 대리 지표**입니다. 실제 사용자 만족·선택 시간은 재지 않았습니다. 그래서 베타에서 보자는 것입니다.
- 골든셋 적중(0.54)은 두 방식이 같았습니다. 기대값이 예전 검수 레시피 50개 기준이라 1,522개 전체에서는 낮게 나옵니다.
- v2는 Jev에 **조리 단계를 보내지 않습니다**(제목·음식 종류·매운맛·난이도·주재료만). #181에서 Jev의 가치가 조리 단계 정보에서 나왔으므로, 조리 단계를 추가하는 것을 베타 중 개선 후보로 둡니다(토큰 증가와 함께 판단).

## 6. 대가와 표시 원칙

- **속도**: 요청마다 Jev 판단 0.2~0.5초가 더해집니다. 애매한 문장은 약 1초입니다. Jev가 응답하지 않으면 규칙 순위로 바로 대체합니다.
- **비용**: 요청 한 번에 Jev 입력 약 3만 토큰입니다. 애매한 문장은 7만~13만 토큰입니다.
- **외부 전송**: 순위를 정하려고 TypeSafe(Jev)에 아래 정보를 보냅니다. #116에서 "계정 취향을 TypeSafe에 보내지 않는다"고 정했으므로, **이 부분은 팀의 명시적인 동의와 개인정보 고지 검토가 필요합니다.**
  - 보내는 것: 요리 실력, 매운맛 취향, 좋아하는·싫어하는 재료 이름, 음식 종류 선호, 요청 문장, 보유 재료 이름(먹을 수 있는 것만), 후보 레시피 요약
  - 보내지 않는 것: 알레르기, 절대 안 먹는 재료, 사용자 id, 레시피 id
- **표시 원칙(#181 권고 반영)**: Jev 점수(0~1)는 확률이 아닙니다. 카드에 퍼센트나 "좋아할 확률"로 보여 주지 않습니다. 항목별 점수는 높음·보통·낮음 같은 구간이나 막대로 보여 주는 것을 권합니다.

## 7. 데이터와 변환 규칙

- **데이터 갱신**: 팀 앱 스냅샷(`b423cc4`)에는 v2가 쓰는 설정(매운 재료 목록·가중치·Jev 질문)과 레시피 맛·난이도·조리시간이 없습니다. 이 저장소의 `scripts/export_v2_bundle.py`로 새 커밋 기준 묶음을 내보냅니다. 출처 커밋과 SHA-256이 함께 나옵니다.
- **레시피 수 차이**: 팀 앱 DB는 1,525개, v2 엔진은 1,522개입니다. 차이는 원자료에 재료가 없는 식약처 레시피 3개(`foodsafety-691`, `-692`, `-831`)입니다. 재료를 모르면 알레르기를 판정할 수 없으므로 v2 경로에서는 추천하지 않습니다(팀 앱 기존 경로에서의 처리는 확인 필요).
- **레시피 id**: 이 저장소 `fs_<일련번호>` ↔ 팀 앱 `foodsafety-<일련번호>`, 이 저장소 `<id>` ↔ 팀 앱 `ontology-<id>`.
- **기존 "원료·분류 제외 8개" → v2 입력**

| 팀 앱 제외 | v2 입력 | 차이 |
|---|---|---|
| 우유·달걀·대두·밀·새우 | 같은 이름의 알레르기 그룹(`milk`·`egg`·`soybean`·`wheat`·`shrimp`) | 같음(포함 가능까지 제외) |
| 생선 | 알레르기 그룹 `fish_bundle`(고등어 + 기타 생선) | 같음 |
| 육류 | 알레르기 그룹 `pork`·`beef`·`chicken` | 팀 앱의 `meat` 하위 판정과 대응. 오리 등 그룹이 없는 고기는 확인 필요 |
| 버섯 | 절대 안 먹는 재료(버섯류) | 버섯은 알레르기 그룹이 아님. 확실히 든 것만 제외. 팀 앱도 버섯 자체만 판정하므로 결과는 사실상 같음 |

## 8. 베타 방식: 팀 앱 변경을 최소로

| 항목 | 내용 |
|---|---|
| 기존 기능 | **그대로 유지.** 8가지 방식 모두 바뀌지 않음. 베타를 켠 사용자에게만 ②④⑥이 v2로 동작 |
| 팀 앱에 추가되는 것 | ① "새 추천(베타)" 토글 ② 서버 경로 1개(새 추천 서비스 호출) ③ 베타용 사용자 정보 입력(알레르기 그룹·절대 안 먹음·매운맛·음식 종류·요리 실력) ④ ②④⑥ 화면에서 베타면 새 경로를 부르는 분기 |
| 추천 로직 위치 | 이 저장소의 엔진을 **별도 서비스**로 띄우고 팀 앱 서버가 호출. 로직이 한 곳에만 있어 팀 앱 코드에 판정 로직이 섞이지 않음. 정식 통합 때는 팀 앱 코드로 옮겨 심을 수 있게 명세와 공용 시험 세트를 준비해 둠 |
| 끄기 | 토글을 끄면 즉시 기존 추천. 접기로 하면 ①~④만 지우면 됨 |
| 회원 데이터 | 팀 앱 DB에만 저장. 새 추천 서비스는 요청 때 받은 정보로 계산만 하고 저장하지 않음(DB 없음) |

- API 키 인증

## 9. 진행 순서와 판단 기준

1. **합의**: 이 문서로 베타 진행, 외부 전송 범위, 서비스 위치, 9장의 결정 사항을 정합니다.
2. **이 저장소 준비**: 8장의 서비스 준비 항목을 진행하고 배포합니다.
3. **팀 앱 베타 PR**: 브랜치에서 작업해 PR로 리뷰받습니다. 토글, 서버 경로, 베타용 입력, ②④⑥ 분기 순서입니다. 기본값은 꺼짐입니다.
4. **선택 참여 기간(예: 2주)**: 팀원과 일부 사용자가 켜서 써 봅니다. 보는 지표는 아래와 같습니다.
   - 새 추천을 켠 비율과 유지한 비율
   - 추천 레시피의 상세 열기·식단 저장·조리 기록 비율(기존 추천과 비교)
   - 알레르기 관련 문제 제보(0이어야 함)
   - Jev 실패율과 응답 시간, 요청당 비용
5. **기본값 켜기 기간(선택)**: 문제가 없으면 기본값을 켜고 끌 수 있게 둡니다. "최대한 메인"이 되는 단계입니다.
6. **결정**: 아래 셋 중 하나를 고릅니다.
   - (가) 정식 통합: 팀 앱 코드로 옮겨 심고(공용 시험 세트 통과가 완료 기준) 기존 ②④⑥ 로직 정리
   - (나) 일부만 채택: 예를 들어 알레르기 27그룹과 매운맛만
   - (다) 접기

## 11. 안전에 대해

- 알레르기 판정에 Jev(AI)를 쓰지 않습니다. 제외는 규칙으로 먼저 끝내고, Jev는 제외를 통과한 레시피 안에서 순서만 정합니다. 제외된 레시피는 Jev가 어떤 답을 해도 다시 나오지 않습니다(테스트로 확인).
- 정체를 모르는 재료가 든 레시피는 알레르기가 있는 사용자에게 보여 주지 않습니다.
- 안전 테스트 일부를 소개합니다.
  - "새우 알레르기면 김치(새우젓 포함 가능)가 든 레시피 제외"
  - "고명·선택 재료라도 알레르기 재료면 제외"
  - "Jev가 목록 밖 레시피를 답해도 무시"
  - "Jev가 실패하면 규칙 순위로 대체"
  - "알레르기 정보는 외부로 보내지 않음"
- 알레르기 안전 테스트 181개는 제가 직접 실행해 통과를 확인했고, 전체 테스트 726개가 통과합니다.
- 정식 통합 때 옮겨 심을 경우, 같은 안전 사례를 담은 공용 시험 세트(`tests/shared/v2_cases.json`)를 팀 앱 테스트가 모두 통과해야 완료로 봅니다.
